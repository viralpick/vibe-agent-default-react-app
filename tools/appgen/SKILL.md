# AgentOS 앱 로컬 개발 → 제품 핸드오프

제품 앱빌더 에이전트 대신 **로컬 Claude Code 가 앱을 만들고, 결과를 제품 스냅샷 체인에 승격**한다. 제품은 그 스냅샷을 샌드박스에 복원해 미리보기를 띄우고, 사람이 배포 버튼을 누르면 대시보드가 된다. 제품 챗에서 이어서 수정한 것은 `pull` 로 되받는다.

**이 경로의 존재 이유는 런타임 검증이다.** 제품 에이전트는 브라우저가 없어 타입 체크와 정적 diff 까지만 한다. 실제로 열어보지 않으면 못 잡는 결함(잘린 라벨, 안 도는 필터)이 남는다. 그걸 안 하면 이 경로를 쓸 이유가 없다.

## 준비

**토큰** (환경별로 따로 저장된다)

```bash
appgen login              # dev
appgen login --env local  # 로컬 스택
```

브라우저 devtools 에서 access token 을 복사한 뒤 실행한다. 토큰 값을 채팅이나 명령줄에 붙여넣지 않는다.

**테넌트 id** 를 사용자에게 받는다. chat 은 아래 흐름의 0단계에서 만든다.

## 흐름

```bash
appgen bootstrap <이름>                    # dev (기본). 로컬 스택이면 --env local
cd local-apps/<이름> && npm install
```

환경은 이때 앱에 박히고 이후 모든 명령이 그것만 읽는다. 전역 기본 환경은 없다.

**0. chat 연결** (앱마다 최초 1회)

```bash
appgen chat create --tenant <id>          # 빈 앱빌더 챗 생성 + 앱 메타에 기록
```

**제품 UI 로 만들지 않는다.** UI 는 프롬프트를 보내야 챗이 생기므로 에이전트 생성 한 턴이 함께 돈다 (LLM 비용, 샌드박스 기동, 곧 덮어쓸 스냅샷). 우리는 빈 챗만 필요하다.

모델은 앱빌더에 노출되는 것(`appBuilderGroup != NONE`) 중에서 고른다. **아무 코드나 넣으면 이후 제품 챗 수정에서 에이전트가 첫 단계에서 죽고, FE 는 "배포에 실패했습니다" 만 보여준다** (실측). `--model <code>` 로 지정할 수 있다.

**이미 있는 챗에 붙일 때**는 이 명령을 쓰지 않고 `push --chat <id>` 로 한 번 알려준다.

**챗 소유자는 로그인한 계정이 된다.** 제품이 챗 소유자만 열 수 있게 막으므로, 고객에게 넘길 앱이면 **고객이 직접 만들고 chatId 를 줘야** 한다.

**1. 온톨로지 탐색** (MCP 툴, bootstrap 이 `.mcp.json` 을 깔아둔다)

```
list_collections → list_objects → get_object_detail → list_object_records
```

`get_object_detail` 이 애드혹 SQL 에 쓸 **3-part FQN 을 함께 준다.** 직접 조립하지 않는다.
`list_object_records` 는 스키마와 실제 레코드를 한 번에 준다 (레코드는 `records.content`).

**2. 쿼리 검증 후 펑션 생성**

```
query_sql  →  create_function
```

`create_function` 은 이 도구의 **유일한 영속 쓰기이고 삭제 엔드포인트가 없다.** 반드시 `query_sql` 로 먼저 검증한다.

**3. 코드 작성 + 런타임 검증**

```bash
appgen servers     # 떠 있나 확인. 떠 있으면 그대로 쓴다
npm run dev        # 없을 때만 띄운다
appgen open        # 토큰과 함께 브라우저로 연다
```

**떠 있는 서버는 그대로 두고 계속 쓴다.** 새로 띄우지 않는다. `npm run dev` 는 3000 이 점유돼 있으면 조용히 3001 로 올라가므로, 이미 띄워둔 것을 잊고 실행하면 **같은 앱을 서빙하는 서버가 두 개** 되고 어느 쪽을 보는지 알 수 없다. 점유자는 로컬 FE 일 수도 있지만 **이전 작업에서 띄워놓고 남긴 내 서버인 경우가 더 많다** (실제로 그렇게 사고가 났다).

브라우저에서 **실제로 동작을 확인한다.** 데이터가 그려지는지, 상호작용이 되는지, 콘솔 에러가 없는지.

**4. 제품으로 승격**

```bash
appgen push \
  --prompt "이번에 무엇을 했는지 한 줄" \
  --title "HISTORY 엔트리 제목" \
  --requirements '[{"name":"기능명","description":"무엇을 어떻게 충족했는지"}]' \
  --plan '[{"title":"단계","description":"그 단계에서 한 일"}]'
```

`chat create` 를 했으면 `--chat` / `--tenant` 가 필요 없다 (앱 메타에 기록돼 있다). 남의 챗에 붙일 때만 `--chat <id>` 를 준다.

로컬 반복은 스냅샷을 만들지 않는다. **"이제 제품에서 보이게 하겠다" 는 시점에만** push 한다.

`--plan` 을 빠뜨리면 제품 챗의 Checkpoint 본문이 빈 채로 뜬다. `--requirements` 를 빠뜨리면 최소 1건이 합성되지만 내용이 부실해진다.

**5. 배포는 사람이 누른다.** 제품 챗의 `Publish` 버튼이다. 로컬에서 배포하는 명령은 없다.

push 나 배포를 마쳤으면, 그리고 사람이 그만하자고 하면 **dev 서버를 정리할지 물어본다.** 조용히 끄지도 말고 그냥 남기지도 않는다 (남기면 다음 작업에서 중복 서버가 된다).

```bash
appgen servers --stop
```

**6. 제품에서 수정된 것 되받기**

```bash
appgen pull        # 워킹트리를 스냅샷으로 덮어쓴다. 덮어쓰기 전 상태는 커밋으로 남는다
appgen status      # 환경, 연결된 chat, 기준 버전 확인
```

push 가 409 를 내면 제품 쪽이 앞서 있다는 뜻이다. `pull` 한 뒤 다시 push 한다 (git 의 non-fast-forward 거부와 같다).

## 반드시 지키는 계약

위반하면 제품 안에서 조용히 깨진다.

| 계약 | 위반 시 |
|---|---|
| `const TENANT_ID` / `FUNCTIONS` / `ACTIONS` 선언 유지 | 제품이 앱의 의존성을 파싱하지 못한다. 런타임에 펑션·액션을 못 찾는다 |
| 모든 주요 요소에 `data-aos-id` / `data-aos-name` | 타겟 수정과 "변경 보기" 가 깨진다 |
| `min-h-screen` / `h-screen` 금지 | 배포 후에도 iframe 안에서 뜬다 |
| 새 npm 패키지 신중히 | 온프렘은 `SANDBOX_OFFLINE=true` 로 `npm install` 을 건너뛴다. 이미지에 없는 패키지면 그 환경에서 깨진다 |
| `.cos/HISTORY.md` 직접 편집 금지 | push 가 번호와 날짜를 부여해 append 한다. 직접 쓰면 번호가 꼬인다 |
| `.env.local` 건드리지 않기 | 로컬 API 주소가 박혀 있다. tar 에서 제외되므로 제품으로 넘어가지 않는다 |

`CLAUDE.md` 에 제품 GUIDE 원문과 오버레이가 있다. 세부 규약은 거기를 본다.

## 함정 (전부 실측)

**id 는 항상 문자열로 다룬다.** AgentOS id 는 64비트라 JS `number` 로 담으면 하위 자릿수가 조용히 뭉개진다. 그러면 서버가 **403 "찾을 수 없습니다"** 로 답해 권한 문제로 오해하게 된다. MCP 툴이 숫자 id 를 거부한다.

**500 의 원인을 추측하지 않는다.** app-api 는 500 을 `"서버 오류가 발생했습니다."` 로 마스킹한다. 컬럼명 오타도, 없는 테이블도 똑같이 500 이다. 좁히는 순서는 `SELECT 1` (연결 확인) → `get_object_detail` 로 실제 컬럼 확인 이다. 스키마를 기억이나 추측으로 쓰지 않는다.

**`tsc --noEmit` 은 이 템플릿에서 게이트가 아니다.** `noUnusedLocals` 가 켜져 있는데 `TENANT_ID` 는 계약상 선언만 하고 쓰지 않는 것이 정상이다. `npm run build` 는 `vite build` 뿐이라 타입 오류로 배포가 막히지도 않는다. **검증의 실체는 브라우저다.**

**dev 포트는 3000 이지만 점유되면 vite 가 조용히 3001 로 올라간다.** 직접 주소를 만들지 않고 `appgen open` 에 맡긴다 — 포트뿐 아니라 **어느 앱인지까지** 확인한다. `local-apps/` 의 앱은 전부 vite 라서, 포트만 보고 열면 다른 앱을 내 토큰과 함께 열 수 있다 (그 앱의 브라우저 히스토리에 토큰이 남는다).

**펑션은 지울 수 없다.** 잘못 만들면 테넌트에 영구히 남는다.

## 하지 않는 것

- **액션 생성·실행** — 제품 앱빌더에도 없다. 사람이 UI 나 온톨로지 챗으로 미리 만들고, 우리는 `list_actions` 로 UUID 만 읽어 코드에 박는다
- **DB 직접 접근** — 온톨로지 펑션과 액션만 경유한다. 행 CUD 는 액션이 유일한 경로다
- **템플릿 레포 파일 편집** — 앱은 반드시 `appgen bootstrap` 사본에서 만든다. 템플릿을 고치면 제품이 스냅샷 없는 신규 앱을 이 레포로 `git reset --hard` 하므로 오염이 전 신규 앱에 번진다
- **템플릿 `package.json` 에 의존성 추가** — 생성되는 모든 앱과 제품 샌드박스로 따라간다
- **환경 오버라이드** — 앱마다 bootstrap 시점에 고정된다. 바꾸려면 새로 bootstrap 한다
